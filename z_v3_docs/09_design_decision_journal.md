# 09. 문제에서 설계 전환까지의 판단 기록

## 1. 목적

이 문서는 단순 누락, 오타, SQL 오류 같은 일반적인 버그를 기록하지 않는다.

현재 방식으로는 구조적으로 해결하기 어렵거나, 한 문제를 해결하면 다른 문제가 커지는 상황에서 어떤 생각을 거쳐 다른 방법을 도입했는지 기록한다. 구현 규격은 `01`~`05`, 남은 작업은 `08`이 책임지며 이 문서는 **판단 과정과 선택 이유**를 책임진다.

각 기록은 다음 질문에 답한다.

```text
무엇을 관찰했는가?
왜 기존 방식의 단순한 값 조정으로 해결하기 어려웠는가?
어떤 다른 방법을 생각했는가?
현재 무엇을 선택했는가?
그 선택의 대가와 다시 검토할 조건은 무엇인가?
```

## 2. 기록 기준

다음에 해당할 때만 추가한다.

- 기존 접근의 구조적 한계 때문에 다른 계층이나 데이터 흐름을 도입한 경우
- 정확도, 설명 가능성, 응답 시간, 운영 안정성 사이의 충돌을 판단한 경우
- 구현할 수 있지만 근거가 부족해 의도적으로 보류한 경우
- 실측 결과가 기존 가정을 반박해 설계를 바꾼 경우
- 향후 같은 문제를 다시 만났을 때 과거 판단 근거가 필요한 경우

다음은 기록하지 않는다.

- 단순 제외 조건 누락
- 변수명, 타입, import, SQL 문법 오류
- 테스트 fixture 자체의 실수
- 기존 문서에 이미 명확한 구현 절차만 있는 작업

상태는 `채택`, `부분 채택`, `검토 예정`, `폐기`로 구분한다.

## 4. 판단 기록

### D01. 온톨로지 규칙 추천에서 계층형 V3로 전환

상태: `채택`

**관찰**

V2는 온톨로지 관계와 정책 점수로 추천 후보를 만들 수 있었지만, 사용자 집단의 행동 패턴을 학습하는 협업 필터링 계층이 약했다. 규칙을 계속 추가하면 추천은 설명하기 쉬워져도 실제 사용자가 함께 소비한 패턴을 스스로 학습하지 못한다.

**기존 방식으로 어려운 이유**

규칙 점수와 가중치를 더 정교하게 조정해도 데이터에서 잠재 취향을 학습하는 모델과 같아지지는 않는다. 반대로 LightFM 하나에 모든 책임을 주면 서비스 filter, 부정 취향, OTT, 설명 근거를 안정적으로 통제하기 어렵다.

**설계 전환**

```text
LightFM     어떤 영화를 추천할지 학습
온톨로지    사용자와 영화의 의미 관계 표현 및 후보 보완
정책 엔진   서비스 조건에 맞게 filter·조정
```

세 계층의 점수와 책임을 섞지 않는 V3를 독립 엔진으로 만들었다. V1은 세밀한 서비스 정책의 우선 비교 기준, V2는 graph·evidence·set-based query의 우선 참고 자료로 사용한다.

**대가와 재검토 조건**

모델 artifact, graph, 후보 snapshot, 정책 버전의 호환성 관리가 필요해졌다. 실제 사용자 데이터에서 hybrid가 규칙 기준선보다 개선되지 않으면 feature와 학습 신호를 다시 검토한다.

관련 문서: [구현 방식](02_implementation_guide.md), [추천 정책](03_recommendation_policy.md)

### D02. 의미 근거와 LightFM 원인을 분리

상태: `채택`

**관찰**

추천 영화에 같은 배우나 장르가 연결됐다고 해서 LightFM이 그 배우나 장르 때문에 점수를 높였다고 단정할 수 없다. 온톨로지 feature를 LightFM 입력에 사용했더라도 최종 내적 점수의 인과적 기여와 사후 의미 일치는 다르다.

**기존 방식으로 어려운 이유**

모든 값을 하나의 `recommendation_score`나 하나의 설명 문자열에 합치면 모델 문제와 정책 문제를 구분할 수 없고, 사용자에게 사실과 다른 추천 이유를 제시할 수 있다.

**선택**

- LightFM raw score
- source별 정규화 점수
- ontology type score와 evidence
- 정책별 가감점
- MMR·반복 감점
- 최종 점수

위 항목을 분리 저장한다. 온톨로지 근거는 의미적 지원과 튜닝 관측 자료이며 LightFM의 인과 설명으로 표시하지 않는다.

**대가와 재검토 조건**

진단 schema가 커지고 해석 도구가 필요하다. 향후 모델 설명 기법을 도입하더라도 ontology evidence와 별도 필드로 유지한다.

### D03. 단기 취향 후보를 장기 후보와 독립 생성

상태: `채택`

**관찰**

범죄 영화를 오래 보던 사용자가 최근 로맨스를 반복해서 보기 시작해도, 저장된 장기 LightFM 후보 100개에 로맨스가 없으면 재정렬만으로 새 취향을 보여줄 수 없다.

**기존 방식으로 어려운 이유**

재정렬은 이미 존재하는 후보의 순서만 바꿀 수 있다. 단기 취향 영화가 후보 집합에 없다는 문제는 가중치 조정으로 해결할 수 없다.

**선택**

최근 positive 행동에서 별도의 온톨로지 후보를 생성한 뒤 장기 후보와 합친다. 단기 변화가 강할 때는 최대 25%의 contextual floor를 적용해 새 후보가 전부 밀리지 않게 한다.

**대가와 재검토 조건**

graph 역조회 비용과 장·단기 점수 정규화가 추가됐다. 단기 후보가 노이즈 행동에 과민해지는지는 실제 행동 데이터로 조정한다.

### D04. 요청 시 단기 계산에서 누적·예약 계산으로 전환

상태: `채택`

**관찰**

단기 취향 후보를 추천 요청마다 계산하면 사용자 한 명의 graph 역조회만으로 수 초가 추가됐다. 단기 취향을 반영해야 한다는 요구가 곧 매 요청 재계산을 의미하지는 않았다.

**기존 방식으로 어려운 이유**

행동 하나마다 즉시 전체 후보를 다시 만들면 Redis를 사용해도 계산량이 줄지 않는다. 반대로 정기 batch만 사용하면 실제 취향 변화 반영이 지나치게 늦어진다.

**선택**

- 24시간 distinct positive 누적
- 영화 3개 또는 가중치 2.0 이상인 영화 2개에서 갱신 자격 획득
- 30초 debounce, 최대 2분 대기
- 예약 worker가 후보를 계산해 Redis에 저장
- passed·OTT는 후보를 재생성하지 않고 최신 filter·정책으로 즉시 반영
- DB 행동 timestamp를 원본으로 유지하고 Redis 장애 시 DB fallback

**대가와 재검토 조건**

갱신 기준 이하의 행동은 기존 후보의 상세 점수에는 반영돼도 독립 후보를 즉시 재생성하지 않는다. 기간, 행동 수, 반감기와 threshold는 실제 freshness·계산량으로 조정한다.

### D05. 벽시계 cache bucket 폐기

상태: `채택`

**관찰**

cache format 2는 6시간 벽시계 bucket을 서명에 포함했다. 성능 측정 중 경계를 지나자 사용자 50명이 동시에 cache miss가 되어 DB fallback 계산을 시작했다.

**기존 방식으로 어려운 이유**

TTL을 늘려도 모든 사용자가 같은 bucket 경계를 공유하면 동시 만료 자체는 사라지지 않는다.

**선택**

벽시계 bucket을 서명에서 제거하고 저장 시점부터 6시간 TTL에 사용자별 결정적 0~30분 jitter를 더했다.

**대가와 재검토 조건**

사용자마다 만료 시각이 달라 운영 시 단일 경계로 상태를 설명하기 어렵다. 대신 synchronized miss를 방지하는 이점이 더 크다고 판단했다.

### D06. OTT를 모델 feature가 아닌 서비스 context로 분리

상태: `채택`

**관찰**

사용자가 특정 OTT를 구독한다는 사실은 그 OTT 영화 장르를 좋아한다는 뜻이 아니다. 영화 제공 상태도 자주 변한다.

**기존 방식으로 어려운 이유**

OTT를 LightFM feature로 넣으면 취향과 접근 가능성이 섞이고, 제공처 변경 때마다 item feature와 모델 artifact 갱신 문제가 생긴다.

**선택**

OTT 구독과 최신 streaming 여부를 학습 feature에서 제외했다. `subscribed_only` hard filter와 `all` 모드 bonus·설명에만 사용한다.

**대가와 재검토 조건**

OTT 안에서 반복적으로 발생한 실제 행동은 direct behavior를 통해 간접 학습한다. 구독 자체를 취향 신호로 다시 넣으려면 별도 실험 근거가 필요하다.

### D07. 전체 dense 점수 행렬 대신 blockwise exact top-K

상태: `채택`

**관찰**

전체 사용자와 약 117만 영화의 점수를 한 번에 만들면 dense matrix가 메모리 한계를 넘는다.

**기존 방식으로 어려운 이유**

후보 수를 줄이기 전에 전체 점수를 materialize하는 구조 자체가 문제이므로 서버 메모리를 늘리는 것만으로 지속 가능하지 않다.

**선택**

사용자 32명과 영화 8,192편 단위 block을 계산하면서 사용자별 exact top-K만 유지한다. 초기 K는 100이었고 hard filter 보충 결정 이후 저장 K는 150으로 확장했다. checkpoint, 사용자별 실패 격리와 결정적 동점 규칙은 그대로 유지한다.

**대가와 재검토 조건**

전체 점수 분포를 한 번에 분석하기는 어려워졌다. 후보 recall ceiling이 부족할 때만 approximate retrieval 또는 상한 조정을 비교한다.

### D08. 고정 분할 대신 4-worker 동적 청크 큐

상태: `채택`

**관찰**

온톨로지 전체 build에서 worker별 고정 범위를 주면 데이터 밀도 차이 때문에 먼저 끝난 worker가 긴 작업을 기다렸다.

**기존 방식으로 어려운 이유**

worker 수만 2개에서 4개로 늘려도 가장 느린 고정 파티션이 전체 시간을 결정한다.

**선택**

의존성이 없는 factual edge stage를 1,000편 단위 공유 큐로 만들고 4개 worker가 끝나는 즉시 다음 청크를 가져오게 했다. semantic aggregate처럼 앞 단계 결과가 필요한 구간은 순서를 유지했다.

**대가와 재검토 조건**

DB write 경합과 worker 장애 복구 관리가 필요하다. 현재 build `22` 전체 시간은 498.3초이며 worker 수는 DB I/O와 메모리 실측 없이 더 늘리지 않는다.

### D09. 장르-only 의미 일치와 품질을 함께 판단

상태: `채택`

**관찰**

공포·미스터리·스릴러 장르-only 사용자에게 세 장르와 overview가 일치하지만 투표가 0~수십 건인 영화가 상위에 올랐다. 기존 품질 점수는 저투표 영화를 높게 보상하지 않았지만 최대 `+0.08` 보너스라 강한 의미 점수를 뒤집지 못했다.

**기존 방식으로 어려운 이유**

품질 bonus만 키우면 행동과 선호 영화가 충분한 정상 사용자에게도 인기작 편향이 커진다. 반대로 전역 최소 투표 수를 적용하면 신작과 희소 영화의 기회를 없앤다.

**선택**

정보가 장르밖에 없는 방어 경로에만 다음 정책을 적용했다.

- vote 0 제외
- vote 20 이상 신뢰 후보 우선, 1~19는 부족할 때만 보충
- 의미 관련도 0.65, 신뢰 품질 0.35
- 선호 장르 포함률 0.70, 영화 내 장르 집중도 0.30
- 의미·overview·장르 관련도·품질·선정 점수 분리 기록

결과적으로 저투표 영화 중심 결과가 `싸이코`, `겟 아웃`, `유전`, `셔터`, `디 아더스` 등으로 바뀌었다.

**대가와 재검토 조건**

장르-only 결과가 세 장르 완전 일치 영화로 좁아지는 문제는 남았다. 신뢰 vote 20과 0.65/0.35는 실제 데이터로 조정할 임시값이다.

관련 진단: [콜드스타트 정책 v3](diagnostics/v3_cold_start_policy_v3_20260827.json)

### D10. 좁은 콜드스타트 해석을 유사 사용자 행동으로 보완

상태: `검토 예정`

**관찰**

정상 온보딩 사용자는 선호 영화가 마블 중심이면 추천도 마블에 집중되고, 장르-only 사용자는 입력한 세 장르를 모두 가진 영화에 집중된다. 현재 입력만 놓고 보면 두 결과 모두 논리적으로 맞지만 사용자의 잠재 취향 범위를 알 수 없다.

**기존 방식으로 어려운 이유**

장르나 선호 영화 가중치를 임의로 낮추면 결과를 넓힐 수는 있지만 무엇으로 넓힐지 근거가 없다. overview도 입력 영화와 후보의 내용 관련성을 설명할 뿐 사용자가 다음에 소비할 다른 방향을 알려주지는 않는다.

**대안 발상**

온보딩이 비슷한 실제 사용자들이 이후 positive 행동을 한 영화를 별도 후보 source로 사용한다.

```text
온보딩 profile
  -> 충분히 유사한 사용자 집단
  -> positive 행동 영화 집계
  -> 사용자 유사도 × 행동 가중치 × 영화별 지지 사용자 수
  -> 유사 사용자 후보
  -> LightFM·온톨로지 후보와 제한적으로 병합
```

`1001`에는 비슷한 사용자가 실제로 소비한 비마블 액션·범죄·SF가, `1009`에는 세 장르 완전 일치가 아니어도 유사 집단이 소비한 공포 또는 심리 스릴러가 들어올 수 있다.

**현재 결정**

실제 사용자와 행동 지지 수가 부족하므로 지금 구현하지 않는다. synthetic seed의 우연한 패턴을 서비스 정책으로 굳히지 않는다. LightFM feature-only도 협업 패턴을 간접 학습하지만, 향후 명시적 유사 사용자 source는 지지 수와 기여도를 통제하고 진단하기 위한 보완 계층으로 본다.

**도입 조건과 안전장치**

- 해당 onboarding profile에 충분한 유효 이웃 수
- 영화별 최소 지지 사용자 수
- 한 사용자의 기여 상한
- passed 제외와 watched·favorite 최종 제외
- `similar_user_score`를 LightFM·ontology와 분리 기록
- 요청마다 전체 사용자를 검색하지 않는 offline 집계 또는 인덱스
- 초기 source 비중 제한과 지지 부족 시 현재 cold-start 유지

구체적인 이웃 수, 영화 지지 수와 병합 비중은 실제 분포를 본 뒤 정한다.

### D11. 무작위 다양성보다 정확도 기준선을 먼저 확정

상태: `부분 채택`

**관찰**

프랜차이즈와 동일 장르 반복을 줄이기 위해 random·신작·롱테일 영화를 섞을 수 있지만, 관련 없는 영화가 들어오면 현재 추천 로직의 정확도 문제와 탐색 정책 효과를 구분하기 어렵다.

**선택**

random replacement는 보류했다. 같은 입력에서 결과를 재현할 수 있는 feature 반복 감점과 결정적 MMR은 유지한다.

**대가와 재검토 조건**

현재 결과는 관련성이 높아도 좁아질 수 있다. 실제 정확도 기준선이 안정된 뒤 exploration을 별도 실험으로 추가한다.

### D12. 방향이 모호한 소셜 행동을 바로 학습하지 않음

상태: `부분 채택`

**관찰**

영화 게시글 작성, 좋아요, 댓글은 영화에 대한 관심은 나타내지만 긍정인지 부정인지 확정할 수 없다. 특히 비판 게시글의 좋아요를 강한 positive로 사용하면 방향이 뒤집힌다.

**기존 방식으로 어려운 이유**

행동 종류만으로 강한/약한 positive를 고정하면 텍스트 맥락과 게시 시점의 playlist 구성을 무시한다. 현재 `likes`에는 `created_at`도 없어 과거 cutoff를 정확히 재구성할 수 없다.

**선택**

raw signal과 provenance는 projector로 진단하지만 모두 `eligible_for_training=false`로 유지한다. direct behavior와 섞지 않고 방향 판정, 시간 정보와 cap 정책이 준비된 뒤 연결한다.

**대가와 재검토 조건**

현재 LightFM은 사용 가능한 소셜 협업 신호를 놓친다. 대신 잘못된 positive로 모델을 오염시키지 않는 것을 우선한다.

### D13. 개별 artifact 활성화에서 serving bundle로 전환

상태: `채택`

**관찰**

새 모델, graph, 후보 snapshot, 정책을 각각 활성화하면 feature mapping이나 build ID가 다른 조합이 요청 중 사용될 수 있다.

**기존 방식으로 어려운 이유**

각 파일이 개별적으로 유효하다는 사실은 조합 전체가 호환된다는 보장이 아니다.

**선택**

model hash와 차원, ontology schema/source, candidate snapshot의 model ID와 게시 건수, feature registry, policy hash를 검증해 immutable serving bundle로 묶는다. `active_bundle.json` pointer만 원자적으로 바꾸고 잘못된 새 pointer는 기존 정상 bundle을 유지한다.

**대가와 재검토 조건**

정책 상수만 바뀌어도 새 bundle 게시가 필요하다. 이 비용을 잘못된 조합의 무음 사용보다 낮다고 판단했다.

### D14. API 버전과 추천 엔진 버전을 분리

상태: `채택`

**관찰**

V3를 독립적으로 만들면서 처음에는 API 쪽에도 V3 디렉터리와 route가 필요해 보였다. 그러나 클라이언트가 사용하는 요청·응답 계약은 바뀌지 않고 추천 내부 구현만 교체되는 작업이었다.

**기존 방식으로 어려운 이유**

추천 엔진이 바뀔 때마다 HTTP API 버전을 늘리면 같은 기능의 route와 schema가 복제되고, 프론트도 내부 구현 버전을 알아야 한다. `app/api/v1`이라는 이름과 추천 엔진 V1은 서로 다른 버전 축이다.

**선택**

기존 API 경로와 `RecommendationResponse`를 유지하고 `RECOMMENDATION_ENGINE` registry가 V1/V2/V3 adapter를 선택한다. 엔진별 import와 분기는 API가 아니라 `app/services/recsys` 아래에 둔다.

**대가와 재검토 조건**

API 경로의 `v1` 표기 때문에 추천 V3가 V1 API를 사용한다는 점을 처음 보는 사람이 혼동할 수 있다. HTTP 계약 자체가 바뀔 때만 API 새 버전을 검토한다.

### D15. V1과 V2를 영역별로 선택해 참고

상태: `채택`

**관찰**

V2는 온톨로지 구조와 집합 기반 쿼리는 발전했지만 이전 평가에서 V1보다 NDCG·Recall이 낮았고, V1에 있던 세밀한 사용자 행동 정책 일부가 약해졌다. 반대로 V1에는 V2의 graph evidence와 build 최적화가 없다.

**기존 방식으로 어려운 이유**

버전 번호가 최신이라는 이유만으로 V2를 기준으로 삼으면 이미 탄탄했던 V1 정책을 잃는다. 그렇다고 V1만 복사하면 V2에서 개선된 graph 구조와 V3에 필요한 새 계층을 사용할 수 없다.

**선택**

- V1 우선: 행동 의미, profile, exclusion, OTT, cold-start, dynamic fill, worker safety
- V2 우선: ontology graph/build/evidence asset, set-based query
- V3 새 결정: LightFM hybrid, source 분리, 독립 단기 후보, serving bundle
- V2 정책은 V1에 대응 항목이 없거나 같은 평가에서 더 낫다는 근거가 있을 때만 선택

결정 출처는 `v1`, `v2`, `v3_new`로 registry에 기록한다.

**대가와 재검토 조건**

한 버전을 통째로 복사하는 것보다 비교 비용이 든다. 대신 정책 회귀를 줄이고 선택 이유를 추적할 수 있다.

### D16. 전체 상세 분석에서 top-100 후분석으로 전환

상태: `채택`

**관찰**

초기 온톨로지 추천은 전체 품질 통과 영화에 대해 edge와 `json_object_agg` 진단을 함께 만들면서 사용자당 약 7초가 걸렸다. 상세 유형과 설명 태그는 최종 결과에는 필요하지만 탈락할 대부분의 영화에 미리 만들 필요는 없었다.

**기존 방식으로 어려운 이유**

단순 index 추가만으로는 전체 후보의 evidence JSON을 조립하는 양을 없앨 수 없다. 반대로 상세 분석을 모두 제거하면 ontology 점수, 부정 취향, OTT 근거와 설명이 최종 순위에 반영되지 않는다.

**선택**

```text
품질 통과 영화 집합
  -> 후보 생성에 필요한 점수만 계산
  -> 최대 100개 선정
  -> 선정된 영화만 set-based 상세 ontology 분석
  -> 정책 재정렬과 설명 저장
```

후보량 500도 검토했지만 상세 분석 비용과 서비스에 필요한 반환량을 고려해 100을 기준으로 정했다. 현재 V3 장기 후보는 blockwise top-150으로 저장해 100개 활성 순위와 50개 예비 순위로 사용한다. 단기·콜드 병합도 순위 후보는 최대 150개지만 상세 분석과 최종 정책 입력은 최대 100개를 지킨다.

**대가와 재검토 조건**

초기 top-100 밖의 영화를 정책 단계에서 구제할 수 없었던 문제가 확인돼 50개 예비 순위를 추가했다. 예비까지 탈락하면 결과 부족을 허용하며 무관한 인기 영화로 강제 충원하지 않는다. 최대 100개의 상세 분석 자체는 현재 약 2~3초 병목으로 남아 있다.

### D17. 온톨로지를 풍부하게 하되 무제한으로 확장하지 않음

상태: `채택`

**관찰**

장르만으로는 추천 근거가 단순하고 다중 장르 영화의 실제 내용을 설명하기 어렵다. actor, director, keyword, theme, mood와 overview 기반 의미를 연결해야 했지만, 관계를 모두 무제한 보존하면 graph 크기와 build 시간이 급격히 증가한다.

**기존 방식으로 어려운 이유**

설명력을 높이기 위해 edge만 계속 추가하면 온라인 조회와 feature matrix가 비대해진다. 반대로 relation을 줄이면 V2에서 정의만 하고 사용하지 않았던 actor·theme·mood 등의 의미가 다시 끊긴다.

**선택**

- genre, keyword, actor, director, theme, mood를 graph·feature·profile·analyzer에 연결
- 사람 node는 공유하되 actor/director relation 역할은 분리
- overview signal은 evidence provenance를 보존
- 영화별 관계군 정규화, feature cap, top-K와 frequency pruning
- canonical edge는 bounded union으로 집계
- build 결과와 feature export를 schema/source hash에 묶어 검증

Build `22`는 3,756,594 node, 12,640,874 edge, 2,078,395 evidence를 498.3초에 생성했다.

**대가와 재검토 조건**

그래프를 풍부하게 만드는 변경은 full build와 feature export를 다시 요구한다. 설명 coverage가 부족한 relation만 근거를 측정한 뒤 추가하며, 단순히 edge 수를 늘리는 변경은 피한다.

### D18. LightFM build 환경과 runtime 환경 분리

상태: `채택`

**관찰**

LightFM 1.17은 Python extension을 빌드해야 해 `python:3.11-slim` 단일 image에서 compiler와 header 의존성이 문제가 됐다. 이를 피하려고 runtime도 전체 `python:3.11`로 바꾸는 방안을 검토했다.

**기존 방식으로 어려운 이유**

전체 image를 runtime에 사용하면 빌드는 쉬워지지만 compiler와 불필요한 패키지가 서비스 image에 남는다. slim만 고집하면 매번 빌드 도구 설치와 정리가 복잡해진다.

**선택**

`python:3.11` build stage에서 LightFM wheel을 만들고, runtime은 `python:3.11-slim`과 `libgomp1`만 사용한다.

**대가와 재검토 조건**

multi-stage Dockerfile과 wheel 호환성 검증이 필요하다. Python 또는 LightFM 버전을 바꿀 때 feature-only 추론과 artifact reload dependency spike를 다시 실행한다.

### D19. 영화 metadata 변경과 graph 갱신 경계

상태: `부분 채택`

**관찰**

장르, 배우, 감독, keyword, overview 같은 영화 metadata가 바뀌면 해당 정보를 복제한 ontology graph와 item feature artifact는 자동으로 최신 상태가 되지 않는다.

**기존 방식으로 어려운 이유**

active graph row를 직접 수정하면 model이 학습한 feature mapping과 serving evidence가 서로 다른 시점을 가리킬 수 있다. 일부 영화만 수정해도 aggregate relation과 source hash의 재현성이 깨질 수 있다.

**선택**

현재 graph는 immutable full build다. source hash가 같으면 성공 build를 재사용하고, graph 영향 원천이 바뀌면 새 비활성 build를 만든 뒤 validation·feature export·model 호환성을 통과한 serving bundle만 활성화한다.

**대가와 재검토 조건**

전체 rebuild 비용이 발생한다. 영화 데이터 변경을 감지해 영향 범위를 판단하고 자동 incremental update 또는 full build를 예약하는 운영 로직은 아직 구현하지 않았으며 중요 후속 작업으로 유지한다.

### D20. 장르 확장을 overview evidence로 검증

상태: `채택`

**관찰**

영화는 여러 장르를 가지므로 선호 장르 하나가 포함됐다는 이유만으로 높은 의미 점수를 줄 수 있다. 장르 node에서 theme·mood를 단순 확장하면 실제 줄거리와 무관한 의미까지 후보에 붙을 수 있다.

**기존 방식으로 어려운 이유**

장르 일치 개수만 조정하면 영화 내용이 중심적으로 해당 장르인지 알 수 없다. overview만 단독 임베딩처럼 사용하면 기존 actor·director·keyword 근거와 설명 가능한 graph 관계를 버리게 된다.

**선택**

명시적 장르 직접 일치는 유지하되, 장르에서 1-hop으로 확장한 theme·mood는 후보 영화의 실제 `overview_signal` evidence가 있을 때만 인정한다. overview support는 ontology raw score와 별도로 기록한다.

**대가와 재검토 조건**

overview가 비어 있거나 품질이 낮은 영화는 의미 확장 기회를 잃는다. 또한 overview는 관련성을 보조할 뿐 영화 품질을 보장하지 않아 D09의 신뢰 품질 정책이 별도로 필요했다.

### D21. 현재 V3 검증에서 NDCG·Recall을 제외

상태: `부분 채택`

**관찰**

이전 MovieLens 기반 평가에서 사용자 수가 늘수록 NDCG·Recall이 낮아졌지만, 입력 행동 변환이 원래 의도한 `5점=saved`, `3.5~4.5=pinned`, `0~1.5=passed`와 다르게 적용된 실행이 있었다. 현재 V3 fixture도 실제 서비스 사용자가 아니라 설계한 행동을 재현한 synthetic 사용자다.

**기존 방식으로 어려운 이유**

잘못된 행동 의미나 synthetic 정답으로 계산한 순위 지표는 숫자는 나오지만 실제 추천 품질을 증명하지 못한다. 이 값을 보고 가중치를 조정하면 fixture 생성 규칙에 과적합될 수 있다.

**선택**

현재 기준선은 다음만 검증한다.

- 사용자 흐름에 맞는 후보 source와 갱신 경로
- 결과 존재, pagination과 응답 계약
- watched·passed·OTT 등 filter 불변식
- score/evidence 분리
- 요청 구간별 응답 시간

NDCG·Recall은 실제 서비스 행동 데이터와 올바른 시간 순서 holdout을 준비한 뒤 측정한다.

**대가와 재검토 조건**

현재 결과가 사람 눈에 자연스럽다는 간이 분석은 가능하지만 정확도 개선을 수치로 주장할 수 없다. production 사용자 학습·평가가 준비되면 이 결정은 종료한다.

### D22. 서로 다른 후보 source의 점수를 먼저 정규화

상태: `채택`

**관찰**

LightFM raw score, 온톨로지 관계 합계, 단기 후보 점수는 범위와 분포가 서로 다르다. 숫자가 크다는 이유만으로 한 source가 항상 이기는 결과가 생길 수 있다.

**기존 방식으로 어려운 이유**

원점수에 고정 상수만 곱해 더하면 모델이나 graph build가 바뀔 때 척도도 변한다. 한 번 맞춘 가중치가 다음 artifact에서 같은 의미를 갖지 않는다.

**선택**

각 source 안에서 후보 점수를 percentile로 정규화한 뒤 장기·단기·콜드스타트 병합 가중치를 적용한다. 원점수는 덮어쓰지 않고 별도 진단 필드로 보존한다. 동점은 source rank와 movie ID로 결정해 재현성을 유지한다.

**대가와 재검토 조건**

percentile은 후보 집합 내부 상대 순위라 절대 confidence를 직접 표현하지 못한다. 향후 calibration 데이터가 충분해지면 source별 확률 보정과 비교한다.

### D23. Passed를 WARP 학습 신호와 분리

상태: `채택`

**관찰**

LightFM WARP는 implicit positive 순위를 학습하는 방식이다. `passed`는 명백한 부정 행동인데 positive interaction matrix에 음수나 낮은 positive처럼 넣으면 의미가 뒤섞인다.

**기존 방식으로 어려운 이유**

positive와 passed가 같은 사용자·영화 pair에 함께 남을 수도 있고, 현재 snapshot schema는 모든 과거 반복 행동 순서를 보존하지 않는다. 임의 음수 weight를 넣는다고 WARP가 명시적 negative 모델로 바뀌지 않는다.

**선택**

- passed는 WARP positive에서 제외
- 동일 pair의 positive/passed 충돌은 passed 우선
- serving hard filter로 즉시 제외
- ontology negative profile과 제한된 감점 근거로 사용

**대가와 재검토 조건**

모델 자체가 negative preference를 직접 학습하지는 않는다. 향후 명시적 negative를 지원하는 모델을 비교하더라도 serving hard filter는 별도 정책으로 유지한다.

### D24. DB를 행동 원본으로, Redis를 파생 상태로 사용

상태: `채택`

**관찰**

Redis `recent_actions`는 빠르게 기록할 수 있지만 TTL, 장애, 재시작으로 유실될 수 있다. DB에는 `pinned_at`, `watched_at`, `passed_at`, `playlist_movies.created_at`이 남아 있고 현재 V3 단기 profile은 이 시간을 사용한다.

**기존 방식으로 어려운 이유**

Redis만 읽으면 DB와 다른 단기 취향이 만들어질 수 있고, cache를 비웠을 때 사용자 상태를 복원할 수 없다. 반대로 모든 예약·후보를 DB 요청 시 계산하면 응답 시간이 길어진다.

**선택**

```text
DB     행동과 timestamp의 원본, 항상 fallback 가능
Redis  pending positive 누적, scheduled/lease 상태, bounded 후보 cache
```

passed와 OTT 변경은 Redis 후보 재계산을 기다리지 않고 최신 DB 상태로 즉시 filter한다.

**대가와 재검토 조건**

DB와 Redis를 동기화하는 worker와 cache signature 관리가 필요하다. Redis에 새로운 파생 상태를 추가할 때도 DB에서 재구성 가능한지 먼저 확인한다.

### D25. 수동 행동 입력 대신 단계별 실제 DB seed 사용

상태: `채택`

**관찰**

장기·단기·부정·콜드스타트 유형을 포함한 144명의 행동을 UI에서 직접 pin·pass·save하는 방식은 반복할 수 없고 입력 실수도 많다. Redis에만 임의 값을 넣으면 실제 추천 흐름을 검증하지 못한다.

**기존 방식으로 어려운 이유**

단일 SQL로 최종 상태만 넣으면 model 학습 전 사용자와 학습 후 cold 사용자를 구분할 수 없다. 추천 API만 반복 호출해도 학습 artifact와 후보 snapshot을 만들 시점이 재현되지 않는다.

**선택**

```text
1단계  training 사용자 120명과 DB 행동 삽입
2단계  hybrid model 학습과 top-150 저장 후보 게시
3단계  model 생성 후 cold 사용자 24명 삽입
4단계  Redis 파생 상태 동기화
5단계  실제 V3 serving path로 응답·흐름·시간 확인
```

seed는 Docker 명령으로 SQL을 삽입하고, Redis는 DB 행동에서 파생해 만든다.

**대가와 재검토 조건**

synthetic 행동은 파이프라인과 정책 시나리오를 검증하지만 실제 정확도를 증명하지 않는다. fixture는 실제 사용자 평가가 준비되면 운영 데이터와 분리해 유지한다.

# V4 Recommendation Architecture and Implementation Plan

## 1. Objective

V4 corrects the ownership of long-term recommendation retrieval without changing
the existing HTTP API contract or removing V1, V2, or V3.

The central rule is:

> Long-term candidates are generated by one Hybrid LightFM lane. Ontology data is
> learned through LightFM user/item features and is not used as a second
> long-term candidate generator.

Direct ontology retrieval remains available only where a learned long-term model
cannot represent the current intent well enough: short-term preference changes
and cold-start.

## 2. Responsibility Boundary

| Stage | Owner | Ontology role |
| --- | --- | --- |
| Long-term candidate generation | Hybrid LightFM | Supplies user and item features to LightFM training and inference |
| Short-term candidate generation | Short-term ontology retriever | Directly searches recent positive-action features |
| Cold-start candidate generation | Feature-only LightFM plus cold-start rules/ontology | Supports users without a learned identity embedding |
| Candidate eligibility | Initial and final filters | Does not generate preference candidates |
| Detailed candidate analysis | Ontology analyzer | Produces semantic match/conflict evidence for bounded candidates |
| Final reranking | Policy engine | Uses separate LightFM score, ontology evidence, and policy effects |

### Prohibited V4 flow

The known-user long-term path must not:

- call `long_term_ontology_retriever`,
- create a `LONG_TERM_ONTOLOGY` candidate lane,
- transfer LightFM lane weight to a parallel ontology lane,
- describe ontology evidence as the causal reason for a LightFM score.

The ontology analyzer after candidate selection is not a candidate generator. It
may adjust final ordering and create explanations, while retaining a separate
score trace.

## 4. LightFM Ontology Feature Contract

V4 is valid only when the loaded LightFM artifact was trained with all three
inputs:

1. Interaction matrix: aggregated user-to-movie behavior labels and confidence.
2. User feature matrix: bounded long-term semantic evidence derived from the
   user's accumulated behavior.
3. Item feature matrix: versioned movie ontology fields such as genre, keyword,
   actor, director, theme, and mood.

Identity features may remain for collaborative filtering, but an identity-only
artifact is not a V4 hybrid artifact. The serving boundary must reject an artifact
whose semantic user/item feature blocks are absent or disabled.

OTT subscription and movie availability remain serving filters. They are not
LightFM ontology features.

## 5. Isolation

- `RECOMMENDATION_ENGINE=v4` selects a separately registered V4 adapter.
- Existing API routes and response schemas remain unchanged.
- V1, V2, and V3 code paths remain runnable and behaviorally unchanged.
- V4 reads only V4-owned model artifacts, candidate snapshots, and serving bundles
  under `assets/ml_models/v4`.
- The V4 serving boundary must validate that the artifact actually
  contains enabled ontology-backed user and item features.
- V4 service and job packages must not import V3 packages.
- V4 owns its retrieval orchestration and has no long-term ontology retriever.
- Model, ontology build, candidate snapshot, and policy versions remain activated
  as one validated bundle.
- Precomputed recommendation rows are scoped by engine so V1, V3, and V4
  candidates do not overwrite one another.

## 6. Implementation Sequence

### V4-01: Engine boundary

- Add the V4 adapter and register `v4` in the common recommendation registry.
- Reuse the existing API contract without adding V4 HTTP routes.
- Add a distinct V4 not-ready error and engine diagnostics.

### V4-02: Hybrid artifact guard

- Validate that both ontology-backed item features and user features are enabled.
- Reject identity-only or semantically empty LightFM artifacts.
- Keep score components and evidence sources separately observable.

### V4-03: Long-term retrieval correction

- Accept only published Hybrid LightFM candidates as known-user long-term input.
- Remove the direct long-term ontology retrieval call from the V4 pipeline.
- Merge only Hybrid LightFM long-term candidates and independent short-term
  candidates.
- Assert that no `LONG_TERM_ONTOLOGY` candidate can enter V4.

### V4-04: Preserve direct ontology exceptions

- Keep the existing short-term refresh/cache/retrieval contract.
- Keep cold-start feature-only LightFM and ontology/rule fallback behavior.
- Keep bounded ontology detail analysis for reranking and explanations.

### V4-05: Verification

- Registry selection: V1-V4 remain selectable.
- Architecture test: known-user V4 never calls long-term ontology retrieval.
- Artifact test: identity-only and disabled-semantic artifacts are rejected.
- Retrieval test: long-term-only, short-term-active, and short-term-inactive paths
  return candidates without a long-term ontology lane.
- Contract test: existing recommendation response and pagination are unchanged.
- Regression test: V3 tests continue to pass unchanged.

### V4-06: Independent offline lifecycle

- Build a V4-scoped ontology schema using `assets/ontology/v4`.
- Export V4 user and item semantic feature matrices.
- Train and publish V4-owned Hybrid LightFM artifacts.
- Materialize and publish `lightfm_v4` top-150 candidate rows.
- Activate an atomic V4 serving bundle under `assets/ml_models/v4`.
- Keep LightFM loss selectable among logistic, BPR, WARP, and WARP-kOS.

## 7. Initial Scope and Deferred Work

This implementation changes candidate-generation ownership and provides the full
V4 build lifecycle. It does not activate a production bundle or alter HTTP API
contracts. Full model, candidate, and serving-bundle publication run only after
the shadow evaluation selects a valid training configuration.

The recommendation storage migration `e7f9a1b3c5d7` is applied locally. Existing
`lightfm_v3` rows were retained as `engine=v3`, and the primary/unique keys now
allow V1, V3, and V4 candidates for the same user to coexist. A rollback-only DB
probe confirmed that an identical user/movie/rank can be inserted for `engine=v4`
without overwriting the V3 row.

The pure logistic LightFM baseline scored NDCG@100%
`0.877307/0.879962/0.880619/0.883570/0.883873` for the same nested cohort sizes.
V4's current default WARP shadow models were lower at every size. Because the
losses differ, this is a baseline finding rather than a final ontology verdict;
the next comparison must hold the cohort, seed, interaction policy, and model
configuration constant while varying loss and semantic features.
